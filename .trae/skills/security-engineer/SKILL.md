# 安全工程师（综合代码质量审查）

以一个「安全工程师」的视角，对代码做一次综合体检，覆盖五大维度：安全审计、注释质量、其它工程质量、代码规范、性能检查。本技能整合以下两个子技能作为检查标准，并补充一般性质量维度。

## 触发条件

- 「安全工程师」「给我做一次代码体检」「综合质量审查」
- 「安全检查 + 注释检查都做一遍」「代码有没有安全问题、注释全不全」
- 要求对某个文件 / 目录 / 本次改动做一次全面审查

## 整合的子技能

| 子技能 | 负责维度 |
|--------|---------|
| security-check（安全检查） | 安全审计 |
| code-check（代码检查） | 注释质量 |
| 本技能的补充维度 | 其它工程质量 |
| 本技能的补充维度 | 代码规范检查 |
| 本技能的补充维度 | 性能检查 |

执行时可读取这两个技能文件以获取详细标准：
- `.trae/skills/security-check/SKILL.md`
- `.trae/skills/code-check/SKILL.md`

## 检查流程（按顺序执行）

### 第 1 步：安全审计（依据 security-check）

1. 敏感信息泄露：硬编码密码、API Key、Token、私钥、数据库连接串；日志/print 打印隐私；测试或注释中夹带真实账号。
2. 注入与漏洞：SQL 字符串拼接注入、命令注入、XSS、路径遍历、不安全反序列化、弱加密（MD5/SHA1 存密码）、硬编码或过短 JWT 密钥、缺失鉴权的敏感接口。
3. 配置明文：`.env` / config 里的明文密钥、默认密码、密钥文件是否被 `.gitignore` 忽略。
4. 其它：CORS 过宽、生产 debug 模式、依赖高危漏洞。

### 第 2 步：注释检查（依据 code-check）

1. 完整性：每个函数 / 方法有无注释说明；重要核心代码块（算法、业务规则、魔法数、复杂分支）有无行内注释；整体注释占比是否约达 30%（10 行代码约 3 行注释）参考线。
2. 准确性：注释是否与代码实际行为一致，有无过时、张冠李戴、改了代码没同步改注释。
3. 通俗性：注释是否让小白 / 非该领域读者也能看懂，而非术语堆砌。

### 第 3 步：其它质量检查（补充维度）

- 死代码：未使用的导入、变量、函数，被注释掉的旧代码大段残留。
- 错误处理：异常是否被吞掉、是否有裸 `except: pass`、资源是否可靠释放。
- 重复代码：明显的复制粘贴（DRY 原则）。
- 复杂度：过长函数、过深嵌套、过多参数，是否存在可拆分点。
- 类型与边界：空值 / 越界 / 除零等边界条件是否处理。

### 第 4 步：代码规范检查

- 命名规范：函数 / 变量用 snake_case、类用 PascalCase、常量用 UPPER_SNAKE；命名见名知意，无拼音与英文混用、无非必要缩写。
- 格式与风格：缩进统一、行长合理；导入按标准库 / 第三方 / 本地分组，且无未使用导入；遵循 PEP8（Python）或对应语言主流规范。
- 魔法值与硬编码：魔法数字、重复出现的硬编码字符串应提取为具名常量。
- 类型标注：关键公共接口有无类型注解，返回值类型是否一致。
- 一致性：同一项目内风格统一（引号、命名、错误处理方式等）。

### 第 5 步：性能检查

- 数据库访问：是否存在 N+1 查询、循环中逐条查询、缺失索引导致的慢查询；大数据量是否分页。
- 阻塞与耗时操作：同步阻塞调用（外部 API / 文件 IO）是否缺少超时、是否阻塞主流程；能否改为异步或并发。
- 缓存与重复计算：可复用的热点结果是否缓存；重复的昂贵计算（编码 / 哈希 / 向量化）是否可预计算。
- 内存：大文件 / 大列表是否一次性读入内存；循环内频繁字符串拼接是否应改用 join；集合是否无界累积。
- 算法复杂度：嵌套循环导致的不必要 O(n²)；查找 / 去重是否可用更高效结构（set / dict）。
- 资源复用：数据库连接、HTTP 会话、文件句柄是否复用、是否可靠释放。
- 并发与并行：相互独立的请求 / 子任务是否并发执行而非串行等待。

## 严重级别（统一）

| 等级 | 含义 |
|------|------|
| 高危/致命 | 真实密钥泄露、可被直接利用的注入、核心鉴权缺失、注释严重误导 |
| 中危/警告 | 弱加密、默认密码、日志泄露、注释缺失或含糊、死代码、错误处理缺失、明显性能瓶颈（N+1 查询、阻塞无超时、大文件全量读内存） |
| 低危/建议 | debug 开启、CORS 过宽、命名不规范、注释可进一步通俗化、复杂度偏高、可优化的性能点（重复计算未缓存、独立的串行等待） |

## 输出格式

最终输出一份统一报告，按五大块组织：

- 一、安全审计（N 处问题）
- 二、注释检查（N 处问题）
- 三、其它质量（N 处问题）
- 四、代码规范（N 处问题）
- 五、性能（N 处问题）

每个问题包含：位置（文件 + 行号）、严重级别、类型、问题描述、影响、修复建议。

报告末尾给「总体结论 + 优先级」：

- 总问题数、按等级统计
- 建议的修复顺序（先修高危，再中危，最后低危）
- 一句话整体评价

## 约定

- 默认只出报告，不修改代码；仅当用户明确要求修复时才动手改。
- 报告语言跟随用户；注释语言建议与项目一致。
- 发现真实明文密钥，必须提醒「该密钥视为已泄露，建议轮换 / 作废，而非仅删除」。
- 示例一律用占位符，不得复制真实密钥、密码、账号到报告中。
