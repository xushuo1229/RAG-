# 代码检查（注释质量审查）

审查代码注释质量，从完整、准确、通俗三个维度检查，并输出结构化报告。

## 触发条件

当用户提出以下需求时调用本技能：

- 「检查一下代码注释」「注释是否齐全」「注释规范检查」
- 「代码注释 review」「注释质量检查」
- 要求按注释标准审查某个文件 / 目录 / 本次改动的代码

## 检查维度

### 1. 注释完整性（是否缺失）

- 每一个函数、方法都必须有注释（docstring 或行内注释），说明：它干什么、关键入参、返回值、可能的副作用或异常。
- 重要的核心代码块必须有行内注释，包括：算法逻辑、业务规则、容易误解的「魔法数」、复杂条件分支、非显而易见的技巧。
- 注释是否需要、写到什么程度，应与其复杂度和重要性成正比：公共接口 / 核心算法要详细，简单的 getter/setter 可从简。
- 参考量化线：整体注释占比约 30%，即每 10 行代码中约有 3 行注释、7 行正文。低于此线通常提示「注释覆盖不足」。
- 注意：量化线是辅助参考，不是逐行硬凑；真正的判据是「每个函数和每段重要逻辑是否都有说明」。

### 2. 注释准确性（是否与代码匹配）

- 注释必须与代码的实际行为一致，不能过时、不能误导。
- 重点排查：
  - 注释说「返回列表」，实际返回字典；写「升序」实际是降序。
  - 复制粘贴后忘记改的注释（张冠李戴）。
  - 代码改了逻辑 / 改名 / 改参数，注释没同步更新。
  - 注释描述的是「计划要做」而非「当前实际实现」。

### 3. 注释通俗性（小白视角）

- 注释应让「不熟悉这段代码 / 该业务领域的人」也能看懂意图，而不是只有专业术语的堆砌。
- 允许使用必要的技术名词，但应当搭配一句「人话」说明它在做什么、为什么这么做。
- 反面示例：
  - `// 调用检索接口`（只重复代码动作，没说明目的）
  - `// 做重排`（有术语无解释）
  - 正面示例：`// 用混合检索（向量+关键词）召回候选，再重排取 top_k，保证答案既有语义相关性也有关键词命中`

## 执行步骤

1. 定位待检查的代码文件：用户显式指定，或默认检查当前改动 / 指定目录下的源码。
2. 逐文件、逐函数、逐核心代码块，按上述三个维度审查。
3. 为每个问题判定严重级别。
4. 输出报告。默认只报告问题、不修改代码；仅当用户明确要求修复时才动手改。

## 严重级别

| 级别 | 含义 |
|------|------|
| 致命 | 函数 / 核心逻辑完全无注释；或注释与代码严重不符，会让读者产生错误理解 |
| 警告 | 注释部分缺失（如只写功能没写参数 / 返回值）；或注释含糊、有术语未解释 |
| 建议 | 注释基本合格但可读性一般，可进一步通俗化 |

## 输出格式

按文件分组，每个问题包含以下字段：

- 位置：文件名 + 行号（或函数名）
- 严重级别：致命 / 警告 / 建议
- 类型：缺失 / 不匹配 / 晦涩
- 问题描述：具体是什么问题
- 原因：为什么这是问题、可能造成什么后果
- 修正建议：给出一个简短的「好注释」示例

报告末尾给出汇总：

- 共检查 N 个文件
- 致命 X 个、警告 Y 个、建议 Z 个
- 整体注释覆盖情况说明（是否达到约 30% 参考线）

## 约定

- 报告语言跟随用户；注释语言建议与项目保持一致（本项目建设中文注释）。
- 只做检查与报告，不主动修改代码，除非用户明确要求。
- 示例一律使用通用占位符，不得夹带真实密钥、路径、账号等敏感信息。
