# 安全检查（代码与配置安全审查）

检查代码与配置文件中的安全隐患，覆盖敏感信息泄露、注入漏洞、明文密钥等，并输出结构化报告。

## 触发条件

当用户提出以下需求时调用本技能：

- 「检查代码安全」「安全审查」「漏洞排查」
- 「有没有敏感信息泄露」「会不会被 SQL 注入」
- 要求按安全标准审查某个文件 / 目录 / 本次改动

## 检查维度

### 1. 敏感信息泄露（代码中）

- 硬编码的密码、API Key、Token、AccessKey/SecretKey、私钥、证书、数据库连接串、内网 IP 等。
- 日志或 print 把密码、token、用户隐私（手机号、身份证等）打印出来。
- 测试用例、示例代码、注释中夹带的真实密钥或账号。
- 版本库里误提交的密钥文件。

### 2. 注入与漏洞风险

- SQL 注入：字符串拼接 SQL、未使用参数化查询（如 `f"SELECT ... {user_input}"`）。
- 命令注入：拼接 shell 命令，或 `os.system` / `subprocess` 直接传入未经校验的用户输入。
- 其他常见漏洞：
  - XSS（前端未转义渲染用户输入）
  - 路径遍历（文件路径由用户输入直接拼接）
  - 不安全的反序列化
  - 弱加密存密码（MD5 / SHA1 无盐）
  - 硬编码或过短的 JWT 密钥
  - 缺少鉴权的敏感接口

### 3. 配置文件明文敏感信息

- `.env`、`application.yml`、`settings.py` 等配置中的明文密钥、默认密码。
- 含密钥的配置文件是否被提交到版本库（检查 `.gitignore` 是否忽略）。
- 配置中的默认账号 / 弱默认密码。

### 4. 其它安全隐患

- CORS 配置过宽（`*` 且允许任意来源带凭证）。
- 生产环境开启 debug 模式，暴露堆栈信息。
- 日志泄露内部路径、请求体等敏感内容。
- 依赖库存在已知高危漏洞（可提示用户核对）。

## 执行步骤

1. 定位检查范围：用户显式指定文件 / 目录；或默认检查关键业务代码 + 配置文件。
2. 按上述维度逐项审查。
3. 为每个问题判定风险等级。
4. 输出报告。默认只报告问题、不修改代码；仅当用户明确要求修复时才动手改。

## 风险等级

| 等级 | 含义 |
|------|------|
| 高危 | 真实密钥泄露、可直接利用的注入、核心鉴权缺失，需立即处理 |
| 中危 | 弱加密、默认密码、日志泄露隐私、路径遍历等风险 |
| 低危/建议 | debug 开启、CORS 过宽、注释里残留但未生效的占位密钥 |

## 输出格式

按类别分组，每个问题包含：

- 位置：文件名 + 行号
- 风险等级：高危 / 中危 / 低危
- 类型：明文密钥 / 注入 / 日志泄露 / 弱加密 / 配置缺陷 / 其它
- 问题描述：具体是什么问题
- 影响：可能造成的后果
- 修复建议：给出具体、可操作的改法（示例用占位符）

报告末尾给出汇总：

- 共检查 N 个文件
- 高危 X 个、中危 Y 个、低危 Z 个
- 整体安全结论

## 约定

- 只做检查与报告，不主动修改代码，除非用户明确要求。
- 发现真实明文密钥 / 已泄露凭证时，必须明确提醒「该密钥视为已泄露，建议立即轮换 / 作废，而不只是删除」。
- 报告中的示例一律使用占位符，绝不复制真实密钥、密码、账号到输出中。
